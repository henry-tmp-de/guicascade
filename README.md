# guicascade

**一个极小、可插拔的 GUI Agent 框架，带步级级联路由。**

核心主张只有一句：**把「这一步该做什么」和「这一步该用多大的模型」彻底解耦。**

---

## 为什么需要它

GUI Agent 很贵——每一步都要把整张截图喂给一个大模型。但轨迹是**不均匀**的：
绝大多数步骤是例行操作，失败只集中在少数几个高风险时刻。

于是有了级联的动机：**默认用便宜的小模型执行，只在监控器发现异常时才升级到
强模型**。省下的是最贵的那部分——模型推理。

代价是必须回答一个新问题：**谁来当这个「发现异常」的人？**
这个判断器必须极轻（每一步都要跑），所以我们把它限制在**文本轨迹**上，
不看截图——轻量、与策略模型无关、每步都能跑。

---

## 架构：五个正交的维度

```
                         ┌──────────────────────────────┐
                         │            Agent             │   核心循环（~150 行）
                         │   问策略要决策 → 交给执行者   │   不知道级联的存在
                         └──────────────┬───────────────┘
                                        │
        ┌───────────────┬───────────────┼───────────────┬────────────────┐
        ▼               ▼               ▼               ▼                ▼
   ┌─────────┐    ┌──────────┐    ┌──────────┐    ┌──────────┐    ┌──────────┐
   │ Policy  │    │ActionSpace│    │  Model   │    │Environment│   │ Monitor  │
   │做什么    │    │怎么说     │    │ 谁来说    │    │ 在哪做    │    │做得好吗   │
   └─────────┘    └──────────┘    └──────────┘    └──────────┘    └──────────┘
    单模型/级联     文本/toolcall    本地/API       安卓/桌面/浏览器   重复/里程碑
```

**换掉其中任何一个维度，其余四个不动。** 配上 `registry.py`，换部件只改 YAML。

| 维度 | 职责 | 关键设计 |
|---|---|---|
| `Policy` | 这一步做什么 | **级联是一个 Policy，不是一个特殊 Agent**——所以三组对照实验共用同一个主循环 |
| `ActionSpace` | 模型的话 → 可执行动作 | 文本解析与原生 tool calling **两条通道并存** |
| `Model` | 产出回应 | 返回 `ModelResponse`：`text` 喂监控器，`tool_calls` 直接构造动作 |
| `Environment` | 动作落到真实界面 | 安卓 / 桌面 / 浏览器 / 离线回放，脏活全关在适配器里 |
| `Monitor` | 该不该升级 | **签名里没有图像参数**——把"只看文本"这个约束固化进类型 |
| `Tool` | 界面之外的通用能力 | 与界面动作分开：前者要重新截图，后者不用 |

## 快速开始

```bash
pip install -e . && pytest        # 46 个测试，0.2 秒，不需要 GPU / 模拟器 / API key
```

**想看它跑起来**，用冒烟配置——全程假模型 + 假环境 + 假监控器：

```bash
python scripts/run_agent.py --config configs/smoke.yaml --env scripted \
    --env-config '{"screens": ["a","b","c","d","e"]}' --task test --max-steps 5
```

会看到监控器报警那一步自动从 `small` 切到 `large`：

```
    0  [small] click(index=1)
    1  [small] click(index=2)      stuck=0.00
    2  [small] click(index=3)      stuck=0.00
    3⬆ [large] click(index=9)      stuck=0.90    ← 升级
```

**跑真实任务**（需要先起模型服务、接上安卓环境）：

```bash
python scripts/run_agent.py --config configs/cascade.yaml \
    --task "把闹钟设到明早 7 点" --trace results/cascade.jsonl
```

三组对照只差一个 `--config`：

| 配置 | 是什么 |
|---|---|
| `configs/single_large.yaml` | 上界：全程强模型 |
| `configs/single_small.yaml` | 下界：全程小模型 |
| `configs/cascade.yaml` | 级联 |

**三者走同一段代码、同一个主循环、同一份日志格式**，所以结果表直接可比。

## 监控器：选型与实测

监控器是级联的判断中枢，也是整个系统里唯一"必须自己搞定"的部件。
我们对可选方案做了一轮实测，结论直接决定了技术路线。

### 实测结果

监控器好不好要用**判别力**说话。我们在两批数据上各测了一遍——这一步很关键：
一个监控器在自己训练时那类环境上灵，**不代表换个环境还灵**。

| 监控器 | 桌面轨迹 AUC | 安卓轨迹 AUC | 结论 |
|---|---|---|---|
| 里程碑 | 0.782 | 0.725 | ✅ 跨环境能迁移，采用 |
| 卡住 | 0.608 | **0.423** | ❌ 弃用，自建替代 |

- **桌面**：47 条真实 Ubuntu 轨迹，按 6 步滑窗构造输入
- **安卓**：本项目**自己在模拟器上跑出来的** 16 条轨迹（小模型 8 条 + 大模型 8 条），
  真值全部来自 `dumpsys` 程序化判分，不含任何人工标注

里程碑的真值构造：正类 = 每条轨迹的**最后一步**（任务跑完必然输出收尾动作），
负类 = 同一条轨迹的中间步。这是任务级真值，不需要人工标注。

> 桌面上的 0.782 是**下界**——中间步里本来就存在真实的里程碑（保存文件、点确认框），
> 它们被当成负类会压低测得的性能。

### 卡住监控器为什么弃用：五条排除

判定一个部件"不能用"需要排除掉所有别的原因，否则结论站不住：

| # | 可能的解释 | 怎么排的 | 结论 |
|---|---|---|---|
| 1 | 我们的实现写错了 | 与参考实现逐位对照 | ❌ 一致 |
| 2 | 输入格式不对 | 训练格式 / 推理格式 / 只喂理由，三种全试 | ❌ 判别力无差别 |
| 3 | 语言问题 | 中英对照，差异 < 0.0013 | ❌ 与语言无关 |
| 4 | **样本选得不对** | 改用真·卡住片段（连续 5 次同动作同坐标） | ❌ 均分仍 0.000001 |
| 5 | **数据本身有问题** | 与轨迹记录格式逐字段核对 | ❌ 格式完全一致 |

第 5 条额外查过：`response` 字段里混着 `</think>` `<tool_call>` 这类 XML
脚手架，怀疑是文本形态不对，试了四种清洗（原样 / 去标签 / 只留理由 /
去所有 XML+JSON），**分数全都贴着 0**。

**五条全排除后，结论是这份权重在其目标概念上不具备判别力。**

安卓数据上还有一条更硬的反证：

    卡住窗口（n=13）  均分 0.976
    正常窗口（n=6）   均分 0.999   ← 反而更高

正常窗口的分数**高于**卡住窗口，AUC 0.423 比随机猜（0.5）还差。
同一个模型在桌面上打出来的分是 ~0（区分不出来），在安卓上是 ~0.99（全都给高分）
——**它响应的其实是"这份输入像不像我的训练分布"，而不是"卡住"这个概念本身**。
这解释了为什么它在桌面上"沉默"、在安卓上"全亮"，也说明这个失效
不是调阈值能救的。

### 替代方案：不加载模型，直接数重复

卡住的判据本质上就是**"同一件事做了好几遍"**。既然判据是现成的，
就没必要用一个 149M 的神经网络去做——`monitors/repeat.py` 只做字符串比较：

- **零参数、零加载、零推理延迟**（对比：BERT 版每步要过一次前向）
- **判据完全可解释**——升级日志里能直接写"因为它把 `click(index=7)` 做了 4 遍"
- 换环境不用重新训练

它同时是神经网络版本的**下界基线**：如果 BERT 版连这个都比不过，就没有上线的理由。

两个模式分别抓两种真实出现的打转形态：

| 模式 | 抓什么 | 例子（实测见过） |
|---|---|---|
| `streak` | 原地不动 | `click(7)` × 8 |
| `count` | 交替打转 | `click(6) click(7) click(6) click(7) ...`（末尾连击永远只有 1） |

### 重复几次算卡住：扫出来的拐点

真值用 `result.txt`（`dumpsys` 程序化判分），**与检测器完全独立**——
不能拿"连续 3 步同动作"当真值去评一个"连续 3 步同动作就报警"的检测器，
那是同义反复。

| N | 失败轨迹命中 | 升级率 |
|---|---|---|
| 2 | 9/9 | 67.6% |
| **3** | **8/9** | **49.5%** |
| 4 | 6/9 | 36.9% |

**N=3 是拐点**：2 召回最高但太贵，4 召回掉得快。

两个反直觉的发现：

1. **"在成功轨迹上触发"不等于误伤。** 分开统计后，"已经正常收尾还被升级"
   几乎为 0。剩下那些触发成功的轨迹，是"重复到撞上步数上限、全靠判分兜住"
   的虚成功——升级它们反而是收益，大模型看一眼就会收尾。
2. **健康轨迹上它一次都不触发。** 大模型跑的那 7 条 2 步收尾的轨迹，
   升级率 **0.0%**。触发全部集中在真正出问题的小模型轨迹上。
   这才是常驻监控器该有的样子：没事不打扰，出事才叫人。

> ⚠️ 一个必须记住的约束：**重复动作在成功轨迹里同样常见**。小模型常常第 1 步
> 就把 app 打开了，然后反复 `open_app` 直到撞上上限。这类轨迹和真卡住的轨迹
> **动作序列完全一样**，差别只在"目标达成没有"。所以这个监控器的定位是
> **升级触发器**，不是"卡住分类器"——它该用三臂对照评，不该用 AUC 评。
> 拿 AUC 评它，等于用错尺子。

### 评测方法论：两条踩过的坑

这两个坑都不是实现问题，而是**评测设计**问题，值得单独记一笔：

**坑一：合成探针不在分布里。** 早期我们手工构造了几十条"很像"的轨迹去测，
得到"监控器完全无反应"的结论。换真实数据后发现，真实 `response` 是上千字符的
完整思维链，合成探针只有 80 字符——**喂进去的根本不是同一类东西**。

**坑二：定义没对齐。** 改用真实数据后，又把"单步轻微冗余"当成了"卡住"。
数据摊开后发现，按严格标准（连续 3 步冗余且动作相同），5000 条轨迹里
命中 **0 个**——那些样本根本不叫卡住，测不出来是理所当然的。

> **结论：定义和分布没对齐之前，任何评测结论都不成立。**
> 这两条现在都固化成了可复现的脚本（见 `scripts/`）。

## 工程笔记

**假件是一等公民。** 模型 / 环境 / 监控器各有一套 `Scripted` 实现，
于是 `pip install -e . && pytest` 在 0.2 秒内跑完 46 个测试，**不需要 GPU、
模拟器、API key**。做出这个选择的理由很实际：没有人会为了看你的代码去配环境。

**环境延迟必须单独量。** 实测安卓模拟器（Pixel 6 / API 33 / x86_64）上各操作的耗时：

| 操作 | 软件渲染 | 宿主机 GPU | 备注 |
|---|---|---|---|
| 执行动作（`input keyevent`） | ~300 ms | ~210 ms | 动作本身很便宜 |
| 截图（`screencap`） | ~2200 ms | ~1920 ms | **单步开销的大头** |
| 无障碍树（`uiautomator dump`） | ~2570 ms | ~2560 ms | **另一个大头** |

三个结论，都是实测出来的：

1. **换渲染后端基本不解决问题**（截图只快 13%，无障碍树没变）。
   一开始我们也以为软件渲染是元凶，测了才发现不是。
2. **截图占了单步开销的近一半**，而级联的监控器本来就不看图——
   纯文本 agent 直接关掉（`AndroidEnv(capture_image=False)`），
   单步从 ~4.5s 降到 ~2.6s。
3. **剩下的瓶颈是无障碍树本身**。`uiautomator dump` 要遍历整棵视图树，
   这是它的固有代价。已知的更快的路子是 AndroidWorld 用的
   accessibility forwarder（走 `-grpc` 长连接），代价是**只在模拟器上可用**——
   我们选了 `uiautomator` 以保住"真机也能跑"，这条权衡记录在此。

这也是为什么 `Step` 里 `latency_model_s` 和 `latency_env_s` 是两个必填字段：
**级联省掉的是前者，后者一分都省不掉。** 在这个安卓环境里，后者比前者还大——
不看这个拆分，会得出"级联没什么用"的错误结论。
